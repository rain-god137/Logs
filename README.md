# LOGS

**LOGS** is a task management and journaling web application built around a single core principle: deliberate daily accountability. Most productivity tools allow tasks to be deferred indefinitely — creating an illusion of organization while enabling procrastination. LOGS eliminates this by enforcing a strict 24-hour task window. Every task must be created and completed within the same calendar day (00:00–23:59). If it isn't done, it expires. There is no reschedule button.

The application combines task management with a journaling system, gamification mechanics, and analytics — giving the user both a workspace and a record of their productivity over time. The goal is not feature richness but behavioral pressure: LOGS is designed to make you confront what you did or didn't do each day. Over time, the heatmap and completion graphs become an honest ledger of your consistency — rewarding streaks and making gaps impossible to ignore.

---

## Features

### Task Management

- Create tasks with rich markdown notes, powered by **Milkdown**
- Write detailed logs for each task: including sub-task breakdowns
- Save task content with `Ctrl + S`
- All tasks expire at **23:59**: tasks can only be assigned and completed within the current day (00:00–23:59)

### Gamification

- Earn **20 XP** per completed task
- Accumulate XP to level up through a progression system
- Track how many consecutive days you have completed at least one task via the **streak counter**

### Analytics & Overview

- **Activity Heatmap**: visual breakdown of task completion across the past 90 days
- **Completion Graphs**: daily task completion rate displayed on the home page for a quick productivity overview

### Journal

- Write and view journal entries in **markdown format** (also powered by Milkdown)
- Log daily insights, reflections, or overviews
- Save journal content with `Ctrl + S`

## File Structure

**`app.py`**: The core Flask application. Defines all routes handling task creation, completion, journaling, XP calculation, streak tracking, and analytics data endpoints. Also manages database initialization and session handling. This is the largest and most central file in the project — nearly all backend logic lives here, from the SQLite queries that fetch daily tasks to the XP accumulation logic that updates on task completion.

**`frontend/index.js`**: Entry point for the Vite frontend. Handles task rendering, the Milkdown markdown editor initialization, and `Ctrl+S` save bindings for both tasks and journal entries. This file bootstraps the frontend on page load and wires up all interactive elements to their corresponding Flask API endpoints.

**`frontend/journal.js`**: Dedicated frontend logic for the journal view. Initializes the Milkdown editor for journal entries and manages save/load interactions with the Flask backend. Kept separate from index.js to isolate journal-specific behavior and keep each module focused.

**`frontend/tasks.js`**: Handles task list rendering, task creation UI, and XP/streak display updates on the frontend. Communicates with Flask routes via fetch calls and updates the DOM in response.

**`frontend/vite.config.js`**: Vite bundler configuration. Defines build output paths so Flask can serve the compiled frontend assets from the `static` directory. This bridges the gap between the Node-based frontend toolchain and the Python backend.

**`templates/`**: Jinja2 HTML templates for all pages — home, tasks, journal, and analytics views. Each template extends a shared base layout, keeping the HTML consistent and avoiding duplication across pages.

**`static/`**: Compiled frontend assets (JS bundles, CSS) output by Vite. These files are generated by running the Vite build and are what Flask actually serves to the browser.

**`instance/`**: Contains the SQLite database file generated at runtime. This directory is created automatically by Flask on first run and is excluded from version control.

**`requirements.txt`**: Python dependencies for the Flask backend. Install with `pip install -r requirements.txt` before running the application.

## Design Decisions

**Why a strict 24-hour task window?** Most task managers allow indefinite deferral, which kills accountability. The decision to hard-expire tasks at 23:59 was deliberate: it forces the user to either complete work or consciously accept failure, rather than silently rolling tasks forward. This mirrors time-boxing principles used in high-output productivity systems. The discomfort of watching a task expire is a feature, not a bug — it creates a feedback loop that makes planning more honest over time.

**Why SQLite over PostgreSQL?** This is a single-user local application. SQLite requires zero configuration, ships with Python, and is sufficient for the data volume involved. Adding a full database server would introduce unnecessary operational complexity for no real gain. Flask's built-in support for SQLite via the `instance/` folder made this an easy decision.

**Why Vite + Vanilla JS over a framework like React?** The frontend interactions are not complex enough to justify a component framework. Vite provides fast bundling and hot reload during development while keeping the output lightweight. Milkdown handles the heaviest UI requirement (markdown editing) as a standalone library. Introducing React would have added abstraction without adding capability for this scope of project.

**Why Milkdown for markdown?** It provides a WYSIWYG markdown editing experience without building a custom editor. It integrates cleanly with vanilla JS and outputs standard markdown that stores well in SQLite. The alternative — a plain textarea — would have made writing and reading task logs significantly worse as a user experience.

**Why XP and streaks?** Raw completion counts don't create behavioral momentum. XP and streaks introduce a feedback loop that makes consistent daily use feel rewarding — borrowing from established gamification research on habit formation. The streak counter in particular is designed to make breaking consistency feel costly, nudging the user toward showing up every day even when motivation is low.

**Why separate the journal from tasks?** Tasks and journal entries serve fundamentally different purposes. Tasks are action-oriented and time-bound. Journal entries are reflective and open-ended. Keeping them as separate modules — both in the UI and in the backend — ensures neither bleeds into the other's design constraints.

## Usage Notes

- **Save shortcut:** `Ctrl + S` saves the current task or journal entry
- **Task window:** Tasks must be created and completed within the same day (00:00–23:59). This is intentional: it enforces proactive planning
